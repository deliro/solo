Solo запускает команду под общей блокировкой в PostgreSQL: одна задача может иметь исполнителей на разных хостах и в разных ЦОД.
Успешный плановый интервал сохраняется в БД, чтобы повторный вызов его пропустил. Запускайте Solo чаще расписания задачи, чтобы повторять неудачные попытки внутри интервала.

## Быстрый старт

Нужны Linux или macOS, общий writable PostgreSQL primary без split-brain и внешний планировщик в UTC.
Роль БД должна иметь DDL-права на схему и чтение/запись таблиц Solo.
Скачайте бинарник из [GitHub Releases](https://github.com/deliro/solo/releases/latest) и добавьте в `PATH`; платформы и проверка контрольной суммы — в [установке](#установка).

```sh
export SOLO_DATABASE_URL='postgresql://solo:change-me@db.example.com/jobs?sslmode=require'
solo run --key reconcile --schedule '*/5 * * * *' -- /bin/echo 'reconcile example'
```

Замените адрес БД и реквизиты через секрет-хранилище, а `/bin/echo` — обработчиком задачи.

Solo выполняет одну попытку. Вызовы и повторы организует внешний планировщик.
Аргументы после `--` передаются напрямую; для доверенного shell-скрипта укажите `/bin/sh -c`.

## Повторы внутри интервала

Вызывайте Solo каждую минуту, оставив задаче пятиминутный интервал:

| Настройка | Значение |
|---|---|
| Kubernetes CronJob `.spec.schedule` | `"* * * * *"` |
| Kubernetes CronJob `.spec.timeZone` | `"Etc/UTC"` |
| Solo `--schedule` | `'*/5 * * * *'` |

Например: в 12:00 ошибка, в 12:01 повтор, в 12:02 успех; в 12:03 и 12:04 — пропуск. В 12:05 начинается новый интервал. Пока предыдущая попытка удерживает блокировку, новые вызовы тоже пропускаются.

Повторы обеспечивает планировщик; Solo делает одну попытку за вызов. После границы окна выбирается новый интервал, старый не догоняется. Обработчик должен безопасно переносить повторное выполнение после сбоя. Подробнее — в [руководстве](docs/usage.md#retry-within-an-interval).

## Установка

Скачайте архив `solo-v<версия>-<target>.tar.gz` и `SHA256SUMS` из [GitHub Releases](https://github.com/deliro/solo/releases).

| ОС | x86_64 | ARM64 |
|---|---|---|
| Linux | `x86_64-unknown-linux-musl` | `aarch64-unknown-linux-musl` |
| macOS 11+ | `x86_64-apple-darwin` | `aarch64-apple-darwin` |

Проверьте SHA-256 архива по `SHA256SUMS` (`sha256sum` на Linux, `shasum -a 256` на macOS), распакуйте его и установите `solo` в каталог из `PATH`. Linux-бинарники статические; для TLS нужны системные корневые сертификаты. Windows пока не поддерживается: управление обработчиком использует Unix-сигналы и группы процессов.

<details>
<summary>Скрипт установки</summary>

Пример установки v0.1.2 для Linux x86_64. Замените `target` значением из таблицы для своей машины; на macOS команды те же. Выполняйте в пустом каталоге:

```sh
(
  set -eu
  version=0.1.2
  target=x86_64-unknown-linux-musl
  archive="solo-v$version-$target"
  release="https://github.com/deliro/solo/releases/download/v$version"
  curl --fail --location "$release/$archive.tar.gz" --output "$archive.tar.gz"
  curl --fail --location "$release/SHA256SUMS" --output SHA256SUMS
  if command -v sha256sum >/dev/null 2>&1; then
    sha256sum --ignore-missing --check SHA256SUMS
  else
    shasum -a 256 --ignore-missing --check SHA256SUMS
  fi
  tar -xzf "$archive.tar.gz"
  mkdir -p "$HOME/.local/bin"
  install -m 755 "$archive/solo" "$HOME/.local/bin/solo"
  "$HOME/.local/bin/solo" --version
)
```

При необходимости добавьте `$HOME/.local/bin` в `PATH`: `export PATH="$HOME/.local/bin:$PATH"`. Сохраните эту строку в файле запуска оболочки. Подключение PostgreSQL и запуск по расписанию описаны выше.

</details>

Сборка из исходников:

```sh
cargo build --release --locked
./target/release/solo --help
```

Нужны стабильный Rust и системный C-компилятор. TLS реализован через rustls с ring; OpenSSL не нужен. Разработка и выпуск версий — в [CONTRIBUTING.md](CONTRIBUTING.md). Лицензия — [MIT](LICENSE).

## Подключение к БД

Поддерживаются URL и строки `key=value`; реквизиты передаются только через `SOLO_DATABASE_URL`.
Поддерживается PgBouncer в режиме transaction pooling с `max_prepared_statements=0`: Solo не требует кеша prepared statements или закрепления соединения за одним backend.
`sslmode` необязателен; по умолчанию используется `prefer`: сначала TLS, при отказе сервера от TLS — незашифрованное соединение. TLS проверяет сертификат и имя сервера через системные CA; ошибка сертификата или имени завершает подключение без перехода на plaintext. Для запрета plaintext задайте `sslmode=require`, для отключения TLS — `sslmode=disable`. Частные CA установите в системное хранилище или задайте через `SSL_CERT_FILE` / `SSL_CERT_DIR`.

## Имя задачи и расписание

`--key` — имя задачи в общей БД. Совпавшие имена делят блокировку со сроком действия (lease) и историю успехов, даже если команды различаются.

| Задача | Ключи |
|---|---|
| Одна задача в двух ЦОД | Одинаковые: `billing/prod/reconcile` |
| Независимые prod и dev | Разные: `billing/prod/reconcile`, `billing/dev/reconcile` |

`--schedule` задаёт расписание для выбора окна выполнения. Оно не запускает команду по таймеру.
Текущий интервал начинается в последний плановый момент не позже времени PostgreSQL.
Например, для `*/5 * * * *` успех в 00:00 подавляет повтор в 00:03; с 00:05 начинается новый интервал.

- Поддерживается пятичастный cron Kubernetes в UTC; подробный синтаксис — в [руководстве](docs/usage.md#schedule-and-outcomes).
- Поздний вызов выполняет текущий интервал; пропущенные интервалы не восстанавливаются.
- Действующая блокировка закрывает весь ключ, включая следующий интервал.
- Все исполнители ключа используют одно расписание; перед его изменением остановите старые запуски.

## Диагностика

```sh
solo status --key hello
```

Нужен только ключ и `SOLO_DATABASE_URL`. Расписание и команда не нужны. Таймаут БД — `--db-timeout` / `SOLO_DB_TIMEOUT`, по умолчанию `3s`.

| Что показывает | Значение |
|---|---|
| `State` | `unknown` — ключ не записан; `free` — свободен; `held` — блокировка действует; `expired` — истекла |
| Владелец | UUID, хост и PID процесса Solo |
| Последняя попытка | Время последнего захвата блокировки, а не начала cron-окна |
| Возраст и остаток lease | Время с захвата и до истечения по часам БД |
| Последнее завершение | Время и результат последней записанной попытки: `success` / `failure` |
| Последний успех | Время подтверждения успеха и соответствующий плановый интервал |

- Команда только читает БД: не запускает миграции, не продлевает и не освобождает блокировки.
- `held` подтверждает lease, но не проверяет, жив ли обработчик. После сбоя завершение может остаться незаписанным.
- Для старых записей отсутствующие данные показаны как `not recorded`.

## Параметры run

CLI перекрывает окружение. Файла конфигурации нет.

| CLI | Окружение | По умолчанию | Назначение |
|---|---|---|---|
| `--key` | `SOLO_KEY` | Обязателен | Имя задачи |
| `--schedule` | `SOLO_SCHEDULE` | Обязателен | UTC-расписание для выбора окна |
| `--ttl` | `SOLO_TTL` | `30s` | Через сколько истечёт блокировка без успешного продления |
| `--heartbeat` | `SOLO_HEARTBEAT` | `5s` | Интервал между началами продления блокировки |
| `--heartbeat-retry-interval` | `SOLO_HEARTBEAT_RETRY_INTERVAL` | `200ms` | Начальная пауза после временной ошибки продления |
| `--max-runtime` | `SOLO_MAX_RUNTIME` | Без лимита | Время работы команды до начала остановки |
| `--db-timeout` | `SOLO_DB_TIMEOUT` | `3s` | Лимит подключения и каждой операции координации |
| `--grace` | `SOLO_GRACE` | `2s` | Ожидание между SIGTERM и SIGKILL |
| `--migration-timeout` | `SOLO_MIGRATION_TIMEOUT` | `10s` | Лимит всей стартовой миграции, включая ожидание блокировки |
| — | `SOLO_DATABASE_URL` | Обязательна | Подключение к общему PostgreSQL primary |

Длительности: `200ms`, `30s`, `5m`, `1h`; положительные, не более 365 дней.
Обязательно `ttl > heartbeat + db-timeout + grace`.
TTL ограничивает срок блокировки, а не работу команды: успешные продления позволяют работать часами.
`--max-runtime` запускает остановку по истечении заданного времени: SIGTERM, затем SIGKILL через `grace`.

Временные ошибки продления повторяются с новым соединением: ошибки соединения/DNS, таймауты, остановка/запуск PostgreSQL, read-only primary, лимит соединений, конфликты блокировок и deadlock. Пауза удваивается от `--heartbeat-retry-interval` до `max(2s, heartbeat-retry-interval)` и сбрасывается после восстановления. На соединение и продление вместе отводится один `db-timeout`, ограниченный последним подтверждённым локальным дедлайном lease минус `grace`. Если следующая пауза уже не помещается, повторы прекращаются; ошибки не продлевают дедлайн. Сигналы и `--max-runtime` продолжают действовать. Диагностика: `phase=heartbeat result=retry` и `result=recovered`.
Потеря владения, ошибки аутентификации, прав, TLS, схемы и неклассифицированные ошибки останавливают обработчик сразу. Захват lease и финальная запись результата не повторяются; завершение обработчика во время сбоя всё ещё требует подтверждённого COMMIT результата.

Завершение обработчика отслеживается и во время продления, и во время паузы перед повтором. Если перед записью результата нужно заменить соединение с БД, Solo подключается один раз; подключение и финальная запись вместе ограничены одним `db-timeout`. Повторного захвата lease и повтора транзакции завершения нет.

## Результат и сбои

| Результат | Код Solo | stderr |
|---|---|---|
| Успех записан в БД | 0 | `result=success` |
| Ключ занят | 0 | `result=busy` |
| Интервал уже успешен | 0 | `result=completed` |
| Ошибка конфигурации, БД, команды, владения, сигнал или лимит | Ненулевой | Этап и причина |

Код 0 означает также штатный пропуск; различайте результаты по stderr.
Диагностика не блокирует управление обработчиком: при переполненном или недоступном stderr сообщения могут теряться, но heartbeat и остановка продолжают работать.
Выход команды с 0 становится успехом только после подтверждённого COMMIT: запись успеха и освобождение блокировки атомарны.

- Исчерпание бюджета повторов heartbeat, постоянная ошибка продления или потеря владения останавливают группу процессов; успех не записывается, код ненулевой.
- Таймаут финального COMMIT также даёт ненулевой код, но БД могла сохранить успех. Следующая попытка проверит историю.
- При ошибке команды Solo пытается освободить блокировку. Если БД недоступна, блокировка истечёт по TTL.
- Истечение TTL само не запускает новую попытку; это работа внешнего планировщика.

## Границы гарантий

- Без доступной БД и захваченной блокировки команда не запускается; просроченный владелец не может продлить её или подтвердить успех.
- Exactly-once и fencing внешних ресурсов нет. Обработчик должен быть идемпотентным: внешнее действие может завершиться до сбоя записи успеха.
- Команда должна оставаться foreground, ждать потомков и держать их в управляемой группе. Solo останавливает группу через SIGTERM/SIGKILL.
- SIGKILL самого Solo на Linux убивает только непосредственного ребёнка через parent-death signal. Очистку всего задания обеспечьте контейнером/оркестратором.
- Долгая пауза процесса, непрерываемая работа ядра и отправленные запросы могут пережить блокировку; failover с потерей данных может удалить историю успехов.
- Solo запускает доверенный код. Ключи не изолируют приложения. Из окружения ребёнка удаляются `SOLO_DATABASE_URL` и `PG*`; не дублируйте реквизиты под другими именами.

## Retention: очистка истории

Retention ограничивает рост истории. Текущий срок — **2928 дней**, единый для всех расписаний.

| Вопрос | Поведение |
|---|---|
| Можно настроить? | Пока нет CLI/env-параметра. Это ограничение реализации, не PostgreSQL |
| Чьи записи удаляются? | Только записи переданного `--key`; другие задачи не затрагиваются |
| Когда? | В транзакции нового захвата. При `busy` и `completed` очистки нет |
| Сколько? | До 1024 записей строго старше срока хранения по часам БД |
| Как выбираются? | По ключу и времени; для этого есть индекс `(key, scheduled_at)`. Найденные строки блокируются и удаляются адресно |
| Есть фоновая очистка? | Нет. Без новых захватов старые записи остаются |

## Эксплуатация

Solo автоматически готовит схему БД при старте. При ошибке или неизвестной версии схемы команда не запускается.
Проверка актуальной схемы не занимает общую блокировку миграций; первая инициализация сериализуется и повторно проверяет состояние под блокировкой.
Обновление схемы, удаление ключей и расчёт места — в [руководстве](docs/usage.md#schema-and-operations).

Справка: `solo --help`, `solo run --help`, `solo status --help`.
